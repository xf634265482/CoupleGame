# 线上派对棋 设计文档

## 1. 背景与目标

打造一款上架微信小游戏的**线上派对棋**，借鉴马里奥派对的聚会体验但具备独立玩法。玩家通过掷骰在棋盘上移动，触发格子事件、参与小游戏，在单局内争夺钻石与金币；局外钻石作为长期货币，为后续外观商城预留能力。

**首版目标**：以最小可玩版本验证「棋盘 + 联机 + 吹牛小游戏」核心循环，2～4 人可完成一整局并正确结算。

## 2. 涉及角色

| 角色 | 核心诉求 |
|------|----------|
| 普通玩家（情侣/单人） | 快速开房或匹配，与 1～3 名玩家完成一局约 20 分钟的派对棋体验 |
| 房主 | 创建好友房、邀请好友、满足条件后手动开始游戏 |
| 系统 | 管理房间生命周期、对局状态权威校验、局外钻石持久化 |

## 3. 功能需求

### 3.1 登录与账号

| 项 | 说明 |
|----|------|
| 触发条件 | 用户首次进入小游戏 |
| 处理逻辑 | `wx.login` + 云开发 `login` 云函数；通过 `OPENID` 创建或加载用户档案（昵称/头像由授权或填写能力提供） |
| 输出结果 | 用户 openId、昵称、头像（来自微信授权）、局外钻石余额 |

### 3.2 大厅与房间

#### 3.2.1 好友房

| 项 | 说明 |
|----|------|
| 触发条件 | 玩家点击「创建房间」 |
| 处理逻辑 | 服务端生成 6 位房间号；房主分享卡片/口令邀请；其他玩家输入房间号或点击分享链接加入；支持 2～4 人；房主配置人数上限（2/3/4） |
| 开局条件 | 房主点击「开始」；当前人数 ≥ 2 |
| 超时处理 | 房间创建后 **5 分钟**内未开始，**自动解散** |
| 输出结果 | 全员进入对局加载页 |

#### 3.2.2 随机匹配

| 项 | 说明 |
|----|------|
| 触发条件 | 玩家点击「快速匹配」 |
| 处理逻辑 | 进入匹配队列；**30 秒**后按当前人数（≥2，最多 4 人）自动开局 |
| 输出结果 | 匹配成功，进入对局 |

### 3.3 棋盘对局（核心循环）

#### 3.3.1 棋盘参数

- **总格数**：72 格，环形
- **结束条件**（满足任一即结算）：
  1. 任意玩家完成 **2 圈**
  2. 对局时长达到 **18 分钟**
- **默认骰子**：1～6（整型随机，服务端掷骰）
- **初始资源**：局内金币 = 0，局内钻石 = 0

#### 3.3.2 格子布局（每局开局随机分配）

| 格子类型 | 数量 | 说明 |
|----------|------|------|
| 钻石格 | 1 | 全图同时仅存在 1 个 |
| 金币格 | 20 | 见 3.3.3 |
| 随机事件格 | 5 | 见 3.3.4 |
| 小游戏格 | 5 | 触发吹牛，见 3.4 |
| 普通格 | 41 | 无事件；钻石格被踩后重生候选池 |

**分配规则**：开局时将 31 个特殊格随机分配到 72 格中的不同位置，其余为普通格。

**钻石格重生**：玩家踩中钻石格获得 +5 钻石后，该格变为普通格；系统在剩余 **41 个普通格**（含刚变普通的格）中随机选 1 格重新标记为钻石格。

#### 3.3.3 金币格

每个金币格在配置时从以下类型中择一（可同类型多格）：

| 子类型 | 效果 |
|--------|------|
| 固定 +100 | 获得 100 金币 |
| 固定 +200 | 获得 200 金币 |
| 固定 +300 | 获得 300 金币 |
| 随机 0～500 | 从 `{0, 50, 100, …, 500}` 均匀随机 |
| 随机 -200～400 | 从 `{-200, -150, …, 400}` 均匀随机（50 的整数倍） |

**厄运降临生效期间**（见 3.3.4）：金币格效果翻转——原「获得 X 金币」变为「失去 X 金币」。

- 固定 +100/+200/+300 → 分别变为 -100/-200/-300
- 随机 0～500 → 按原随机结果 X 变为失去 X（X ∈ {0, 50, …, 500}）
- 随机 -200～400 → **固定失去 200 金币**（取区间内最大负值 -200）

#### 3.3.4 随机事件格

首版仅 1 种事件卡：

**厄运降临**

- 触发：玩家踩中随机事件格并抽取（首版 100% 为此事件，或等权重仅 1 种）
- 效果：全局生效，持续 **2 个完整回合**（从触发玩家下一回合起计，至第 2 回合结束后失效）
- 影响：所有金币格按 3.3.3 厄运规则处理

#### 3.3.5 回合流程

```
当前玩家回合开始
  → 掷骰（1～6，服务端）
  → 移动棋子
  → 触发落点格子事件（可能进入小游戏子流程）
  → 检查结束条件（2 圈 / 18 分钟）
  → 切换下一位玩家（顺时针）
```

**回合制同步**：所有客户端展示相同棋盘状态；操作指令上报服务端，服务端校验后广播状态快照。

#### 3.3.6 胜负与结算

| 优先级 | 规则 |
|--------|------|
| 1 | 局内 **钻石** 多者胜 |
| 2 | 钻石相同，比较局内 **金币** |
| 3 | 仍相同，**显示平局** |

**局外结算**：本局获得的局内钻石累加至用户 **局外钻石** 余额（首版无消费入口，仅持久化）。

### 3.4 小游戏：吹牛（大话骰简化版）

#### 3.4.1 触发

玩家踩中小游戏格，当前棋盘回合暂停，全员进入吹牛子对局。

#### 3.4.2 规则概要（标准简化版）

| 项 | 规则 |
|----|------|
| 人数 | 与当前棋盘对局人数相同（2～4 人） |
| 骰子 | 每人 5 颗骰子，摇完后隐藏，仅自己可见 |
| 叫点 | 轮流出价「全场至少有 N 个 P 点」（N 递增，P 为 1～6）；1 点作万能（赖子）——首版采用最常见规则 |
| 开 | 下家可选择「开」质疑上家；开牌统计，判定失败者出局 |
| 结束 | 直至剩 1 人为止，按出局顺序 **倒序排名** |

#### 3.4.3 奖励（局内金币）

按 **实际参与人数** 发放，**最后一名无奖励**：

| 名次 | 2 人局 | 3 人局 | 4 人局 |
|------|--------|--------|--------|
| 第 1 名 | 800 | 800 | 800 |
| 第 2 名 | — | 500 | 500 |
| 第 3 名 | — | — | 200 |
| 末位 | 0 | 0 | 0 |

#### 3.4.4 返回棋盘

小游戏结束后，所有玩家回到棋盘，由 **下一位玩家** 继续棋盘回合（触发者本回合已在落点完成）。

### 3.5 退出与判负

| 场景 | 处理 |
|------|------|
| 玩家主动退出 / 掉线（首版无重连） | 该玩家 **判负** |
| 对局 | **立即结束**，按当前状态 **强制结算** |
| 其他玩家 | 正常获得局内钻石/金币，局外钻石按结算写入 |

## 4. 边缘场景与异常处理

| 场景 | 处理策略 |
|------|----------|
| 好友房 5 分钟未开始 | 自动解散，提示「房间已过期」 |
| 对局中有人退出 | 退出者判负，全员立即结算 |
| 18 分钟到时且无人完成 2 圈 | 按当前钻石/金币排名结算 |
| 多人同时完成 2 圈条件 | 以服务端先检测到者为准，或同回合内均算完成 |
| 钻石格被踩时该格为唯一普通格 | 不可能（41 普通格 >> 1）；若极端情况由服务端跳过重生并打日志 |
| 厄运与负金币 | **允许**局内金币为负数 |
| 吹牛超时 | 服务端回合倒计时 **30 秒**，超时自动「开」 |
| 微信登录失败 | 提示重试，不可进入联机 |
| 网络短暂中断 | 首版不做重连；视为退出判负 |

## 5. 技术方案

### 5.1 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    微信小游戏客户端                        │
│              Cocos Creator 3.8.8 (CoupleGame)            │
│  大厅 │ 房间 UI │ 棋盘渲染 │ 吹牛 UI │ 结算页              │
│  wx.cloud.callFunction + 云数据库 watch                   │
└──────────────────────────┬──────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────┐
│                    微信云开发                              │
│  云函数：login / room / match / game / scheduler          │
│  云数据库：users / rooms / games / match_queue            │
└─────────────────────────────────────────────────────────┘
```

**客户端**：现有 `CoupleGame` Cocos Creator 工程，发布为微信小游戏。

**服务端**：**微信云开发**（云函数 + 云数据库 + 定时触发器），详见 `plan.md`。

**权威服务端**：掷骰、移动、格子效果、吹牛判定、结算均在云函数内计算；客户端通过 `callFunction` 发指令、`db.watch` 收状态，仅展示与发送意图。

### 5.2 核心流程

#### 5.2.1 好友房开局

```
房主创建房间 → 生成 roomId → 玩家加入 → 房主点开始
  → 服务端校验人数≥2 → 初始化棋盘（随机格子）→ 广播 GameStart
  → 进入回合循环
```

#### 5.2.2 棋盘回合

```
Client: RequestRollDice
Server: 校验回合权 → 随机 1～6 → 更新位置 → 解析格子事件
  → 若小游戏：切换 GamePhase=MINIGAME
  → 否则：应用金币/钻石/事件 → 检查结束 → 广播 StateUpdate
```

#### 5.2.3 对局结束

```
触发结束条件 → Server 计算排名 → 写局外钻石 → 广播 GameOver
  → 客户端展示结算页 → 返回大厅
```

### 5.3 数据结构

#### 5.3.1 用户（云数据库 `users` 集合）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | string | 应用层雪花 ID，非自增 |
| _openid | string | 云开发自动注入，唯一 |
| nickname | string | 昵称 |
| avatarUrl | string | 头像 URL |
| diamond | number | 局外钻石余额 |
| createdBy / createdDate / updatedBy / updatedDate | | 审计字段 |

> **数据隔离**：按微信 openId **全局一份**用户档案，非多租户 SaaS，无需 `unit_id`。  
> **首版无对局历史表**，仅持久化局外钻石。

#### 5.3.2 对局状态（运行时）

| 字段 | 说明 |
|------|------|
| room_id | 房间 ID |
| players[] | 玩家列表：openId、座位、位置、圈数、金币、钻石、在线状态 |
| board_cells[72] | 格子类型及子配置 |
| diamond_cell_index | 当前钻石格索引 |
| current_turn | 当前回合玩家座位 |
| doom_remaining_turns | 厄运剩余回合（0 表示未激活） |
| phase | BOARD / MINIGAME_BLUFF / SETTLED |
| started_at | 开局时间（18 分钟计时） |
| minigame_state | 吹牛专用状态 |

#### 5.3.3 金币格子配置枚举

```
FIXED_100 | FIXED_200 | FIXED_300 | RANDOM_0_500 | RANDOM_NEG200_400
```

## 6. 验收标准

- [AC-1] 用户可通过微信登录进入大厅，展示昵称与头像
- [AC-2] 用户可创建好友房，获得房间号，其他用户可加入
- [AC-3] 好友房满足 ≥2 人且房主点击开始后，全员进入同一局棋盘
- [AC-4] 好友房 5 分钟未开始自动解散
- [AC-5] 用户可通过快速匹配与其他玩家开局（2 人可开）
- [AC-6] 72 格棋盘每局随机分配：1 钻石 / 20 金币 / 5 事件 / 5 小游戏 / 41 普通
- [AC-7] 回合制流程正确：掷骰 → 移动 → 触发事件 → 切换下家
- [AC-8] 金币格五种数值及 50 整数倍随机正确；厄运降临 2 回合内效果翻转正确
- [AC-9] 钻石格 +5 钻石，被踩后在普通格随机重生，全图始终 1 个钻石格
- [AC-10] 踩小游戏格进入吹牛，2～4 人排名奖励正确，末位无奖
- [AC-11] 完成 2 圈或 18 分钟到时触发结算，钻石优先、金币次之
- [AC-12] 局内钻石正确累加至局外钻石余额
- [AC-13] 玩家中途退出，该玩家判负，对局立即结束并结算
- [AC-14] 掷骰与数值变更以服务端为准，客户端无法篡改结果
