## 一、定位

本文档覆盖**工程性能层**——非玩法/数值设计，而是「玩家点开小游戏到能玩为止」这条主路径的耗时/包体/真机兼容问题。范围：

1. **启动主路径**（bootstrap → 登录 → 资源 → 大厅）的串/并行编排与可优化点。
2. **微信小游戏分包策略**：`assets/resources` → `resources` 微信分包 + 主包 critical native 复制清单。
3. **真机兼容陷阱**：分包 native 不可读、`Error 4930`、主包 4MB 红线、补丁顺序。
4. **资源加载链**：`UiAssets.ts` 多重回退（native 主包 → 分包 copyFile → bundle.load → UUID），及 BGM 真机走 `InnerAudioContext`。
5. **运行时性能**：场景切换、preload 批次、scheduler/RNG 复算开销（PVE）。

玩法相关的耗时（如 PVE 战报回放节奏 120ms/80ms）属于「手感调优」，归 [UI设计与交互V1](UI设计与交互V1.md) §7.3，本文档不重复。

## 二、启动主路径（GameApp.onLoad）

`assets/scripts/core/GameApp.ts` 的 `onLoad` 是冷启动权威编排：

```
lockPortrait → 2 帧 refreshScreenAdapt
  ├─ wx 不可用（编辑器预览）→ ensureResourcesBundle → tryStartBgm → 2s 后 SceneLoader.loadLobby()
  └─ 微信运行时 →
       initWxCloud
       Promise.all([ login(), ensureResourcesBundle() ])   // 关键并行：网络 + IO
       Promise.race([ preloadLobbyUi(), 1500ms ])          // 软上限：到点先进大厅
       SceneLoader.loadLobby()
       void preloadLobbyUi 继续后台跑                        // 缺图由 LobbyController 异步回填
       void preloadLobbyBackgroundAssets()                  // 后台预热房间/棋子
       void tryStartBgm(bundle)                             // 后台启动 BGM
```

### 2.1 关键设计原则

- **登录与资源加载并行**：原本 `login()` 串 `ensureResourcesBundle()` 是默认顺序，但二者**互不依赖**（云开发初始化已完成、bundle 加载是纯 IO），改 `Promise.all` 后冷启动主路径少一段串行。
- **首屏只阻塞最小集**：`preloadLobbyUi` 只拉 `LOBBY_ESSENTIAL_KEYS = bg_lobby + 6 个大厅 UI`，其余（房间背景/卡片/棋子）由 `preloadLobbyBackgroundAssets` **fire-and-forget 后台预热**——玩家点"创建房间"前几乎必然加载完。
- **大厅首屏软上限 1500ms**（2026-06-11 优化）：原本 `await preloadLobbyUi()` 强阻塞，真机最坏 5~7s 黑屏。改为 `Promise.race([preloadLobbyUi(), 1500ms])` —— 1.5s 内能加载完就常规流；超时则先 `SceneLoader.loadLobby()` 进大厅，剩余图后台继续 preload，`LobbyController` 内 `loadUiSprite(key).then(paint)` 的回填模式（如 `_applyRoomSlotPawn`）会自然补刷；首帧可能出现 Graphics 占位色块，按钮文字仍可点。
- **大厅首屏图并行加载**（2026-06-11 优化）：`preloadLobbyUi` 7 张主包 native 小图改用 `preloadKeys(..., { parallel: true })` 一次性并行，绕开 `PRELOAD_BATCH_SIZE=6` 分批限制；分批限制对重资源（房间/结算大背景）仍保留。
- **BGM 异步启动**：`void this._tryStartBgm(bundle)` 不阻塞 `loadLobby()`，避免首屏被 BGM 加载阻塞。
- **任一关键失败 → 文案兜底**：bundle null → `资源包加载失败，请清缓存后重试`；登录抛错 → `登录失败：${msg}`。**不重试、不静默吞错**，让用户能据此决策清缓存。

### 2.2 已知可优化点（M2 待办）

| 项 | 现状 | 思路 |
|---|---|---|
| `initWxCloud` 与 `Promise.all([login, ensureResourcesBundle])` 串行 | cloud init 必须先于 login（云开发依赖） | 可考虑把 `ensureResourcesBundle` 提前到 `initWxCloud` 之前（资源加载与 cloud init 互不依赖） |
| ~~`preloadLobbyUi` 阻塞 `loadLobby()`~~ | 2026-06-11 已改为 1500ms 软上限 race | （完成）后续可改进：LobbyController 监听 `lobby-ui-ready` 事件统一 rebuild，免回填遗漏 |
| 大厅 → 棋盘切换时若 `preloadLobbyBackgroundAssets` 未完成 | 当前 `LobbyController` 不等待 | 可在创建房间按钮上加 spinner 提示 |

## 三、微信分包与主包 4MB 红线

### 3.1 分包结构（补丁后）

```
build/wechatgame/
  assets/resources/              ← 主包 stub
    index.js, game.js, config.json
    import/                      ← 从分包复制（JSON 索引）
    native/                      ← copyCriticalNativeToMain：大厅/棋盘 UI + icons + bg_lobby + BGM
  subpackages/resources/         ← 全量重资源（含大背景、结算；icons 亦有副本供 devtools）
    import/, native/, config.json, index.js, game.js
```

### 3.2 资源分布策略

| 资源 | 位置 | 原因 |
|------|------|------|
| 大厅/房间/棋盘 UI 按钮、面板、卡片 | **主包** native | 须即时显示，分包 copyFile 真机常失败 |
| `bg_lobby`（压缩后 ~272KB） | **主包** | 启动首屏即用 |
| `bg_board`（压缩后 ~200KB） | **主包** | 进棋盘须立即显示 |
| `bg_room` / `bg_settlement` / `settlement/*` | **分包** | 单张未压缩 ~2MB，主包装不下；进场时异步加载 |
| `icons/*` | **主包** + 分包副本 | 说明弹窗/HUD 角标须即时；分包 copyFile 真机每次重试 ~2s |
| BGM mp3（96kbps，~500KB） | **主包** | 真机 `InnerAudioContext` 直读包内路径，不能 `bundle.load` 分包 mp3 |

### 3.3 4MB 主包红线

微信小游戏单包硬上限 4096KB。当前 critical native 清单（大厅+棋盘+icons+bg_lobby+bg_board+BGM）压缩后约 3.x MB，**剩余余量很小**。增删 critical 项前必须：

```bash
python scripts/compress-ui-large-assets.py   # 大图压缩（背景 ≤400KB/张，BGM 96kbps）
python scripts/calc-main-native-budget.py    # 主包体积估算（est main slim < 4096 KB）
node scripts/patch-wechatgame-config.js      # 重跑补丁
```

`MAIN_NATIVE_EXCLUDE_*` 排除：`bg_room`、`bg_board`、`bg_settlement`、`settlement/*`。**icons 不得排除**。

## 四、构建后补丁（patch-wechatgame-config.js）

每次 Cocos Creator 构建 wechatgame 后**必须**跑 `node scripts/patch-wechatgame-config.js`。补丁分十步，顺序敏感：

| 步骤 | 作用 |
|------|------|
| `ensureResourcesSubpackage` | 把 `assets/resources` 配置为微信分包 `subpackages/resources` |
| `patchEngineResourcesSubpackage` | engine-adapter 中 resources bundle 基路径改为 `subpackages/resources/` |
| `patchEngineResourcesConfigInMain` | config 从主包 `assets/resources/config.*.json` 读取 |
| `patchEngineSubpackageFileExists` / `patchWebAdapterSubpackageExists` | 分包路径跳过 exists 误报 |
| `patchEngineTransformImportRewrite` | import URL 重写到 `assets/resources/import/`；**移除 native `/` 前缀**（规避 4930） |
| `copyResourcesImportToMain` | 物理复制 `import/` JSON 索引到主包 |
| `ensureResourcesEntryScripts` | 写主包 stub；**strip** 多余目录（注意：勿删后续要写入的 native） |
| `buildCriticalNativeManifest` + `copyCriticalNativeToMain` | 从 `UiAssets.ts` 的 `UI_SPRITE_UUID` 自动生成清单，把对应 native 文件复制进主包 |
| `syncProjectConfig` | 不 ignore 主包 native（`packOptions.ignore` 不得排除 `assets/resources/native`） |
| `verifyJsSyntax` | `node --check` engine/web adapter，避免补丁后语法错误 |

### 4.1 顺序陷阱（事故根因之一）

`copyCriticalNativeToMain` **必须**在 `ensureResourcesEntryScripts` **之后**——后者会 strip 多余目录，若顺序反了 critical native 会被删空，真机大厅按钮全无。

### 4.2 补丁自检清单

```
[ ] python scripts/calc-main-native-budget.py → est main slim < 4096 KB
[ ] node scripts/patch-wechatgame-config.js   → exit 0，日志含
    · build structure OK
    · critical native manifest（从 UiAssets.ts UUID 派生）
    · est. main ~xxxx KB（< 4096）
[ ] build/wechatgame/assets/resources/native/  含 board/ 对应 uuid 文件
[ ] build/wechatgame/assets/resources/import   存在
[ ] 真机：大厅按钮 + BGM + 棋盘按钮/格子/棋子
[ ] 真机控制台：patched downloadDomImage strip-leading-slash
```

## 五、运行时资源加载链（UiAssets.ts）

`loadUiSprite(key)` 按运行环境选不同回退链：

| 环境 | 加载顺序 |
|------|------|
| 编辑器（EDITOR） | `loadByUuid` → `loadFromResources` → `loadFromMainBundle` |
| 微信真机（`usesWechatNativeFs`） | `loadWechatNativeSprite`（主包 native 优先，分包 copyFile 兜底）→ `loadFromMainBundle` |
| 微信开发者工具 | `loadFromResources` → `loadFromMainBundle` |
| 浏览器/普通 Web | `loadFromResources` → `loadFromMainBundle` → `loadByUuid` |

### 5.1 关键不变量

1. **真机禁止 `bundle.load` 读分包贴图**——会触发 `Error 4930`。分包 native 只能走 `wx.getFileSystemManager().readFile/copyFile` 复制到 `USER_DATA_PATH` 再 `wx.createImage`。
2. **真机首选主包 native**——`MAIN_NATIVE_ROOT = assets/resources/native`，`copyFile` 到 `${wx.env.USER_DATA_PATH}/couple-ui-${uuid}.png` 后 `createImage`。
3. **`downloadDomImage` 补丁仅去 URL 前导 `/`**——禁止 `readFile` 拦截分包贴图。
4. **预加载真机分批**：`PRELOAD_BATCH_SIZE=6`，并行过大会压垮微信 fs；devtools/浏览器无此限制。
5. **分包 only 资源跳过 preload**：`WECHAT_SUBPACKAGE_ONLY_KEYS` 含 `bg_settlement` + `settlement/*` 前缀；`preloadBoardUi` 真机过滤掉这批。
6. **分包下载等待**：`wx.loadSubpackage` success 常早于 native 落盘；真机等额外 `WECHAT_REAL_DEVICE_SUBPACKAGE_SETTLE_MS=1000ms`，`bytesExpected=0` 时再加 `WECHAT_SUBPACKAGE_ZERO_BYTES_EXTRA_MS=1000ms`（2026-06-11 从 2000/3000 ↓，回归冒烟未见 native 缺失即可定稿；若复发再调回）。

### 5.2 分包-only 资源加载（结算/房间背景）

走 `applyScreenBackground(canvas, 'settlement')` 异步——进场即建占位 `Graphics`，图加载好后再覆盖。**禁止**在 controller 构造时阻塞等图（否则进场卡住）。

## 六、BGM 加载（BgmController.ts）

- 真机：`InnerAudioContext` 直读主包 mp3（`audio/bgm_main.mp3`），**禁止** `bundle.load('audio/bgm_main')` 走分包 stat（会 `stat:fail`）。
- BGM 压缩到 96kbps（~500KB），由 `compress-ui-large-assets.py` 处理。
- BGM 启动是 `void` 异步，不阻塞 `loadLobby()`。

## 七、真机现象 → 排查映射

| 现象 | 处理 |
|------|------|
| 仅背景有图、按钮纯色 | 对应 UI native 未进主包；查 patch 日志 `critical native -> main lobby/btn_...` |
| 棋盘格子/按钮/棋子全无 | 棋盘 UI 未进主包；确认 manifest 含 `board/*`；重建 + patch |
| `Error 4930 subpackages/...png` | 真机误走 `bundle.load` 或 Image 直读分包；改回 `loadWechatNativeSprite` 主包优先 |
| BGM `stat:fail` 分包 mp3 | 真机勿 `bundle.load` BGM；用主包 mp3 + `playWechatBgm` |
| `native sprite unavailable` 主包路径 | patch 顺序错或 native 被 strip；重跑 patch |
| 真机调试 `ENOENT assets/resources/native/...` | patch 须含 `writeCompileNativePlaceholders`（占位 PNG，非完整复制） |
| 主包超 4MB（4970KB 等） | 勿 `copyMissingNativeToMain` 复制大背景；`packOptions.ignore` 不计入上传体积 |
| `readFile:fail` 分包 native | 大背景预期行为；`preloadBoardUi` 已跳过；背景走 `applyScreenBackground` 异步 |
| 进棋盘很慢 | 历史问题——曾并行 preload 40 次分包重试；现 icons 进主包 + 重试 8 次 + 跳过 `bg_board` preload |
| `compiled UiAssets patch skipped` | Cocos 重建 wechatgame |
| patch 后无 `critical native -> main` | `copyCriticalNativeToMain` 须在 `ensureResourcesEntryScripts` **之后** |
| `readFile:fail no such file "src/effect.bin"` + `cc.game.start failed` | **本地构建产物 effect.bin 时间戳过旧**：Cocos 增量构建保留旧文件 + 微信工具 mtime 增量上传跳过 → 真机端缓存无此文件。修法：`rm build/wechatgame/src/effect.bin` 后 Cocos Creator 重新构建 → patch → 清缓存编译 → 预览。**禁忌**：不要去关 `customPipeline` 或删 `effectSettingsPath` 绕过——会导致模拟器 `batcher2D switchBufferAccessor of null` 渲染挂掉（2026-06-11 教训） |

### 7.1 渲染管线 customPipeline 禁忌（2026-06-11 教训）

`src/settings.json` 的 `rendering.customPipeline=true / effectSettingsPath='src/effect.bin'` 由 `patchRenderingSettings` 强制写入，**禁止关闭或删除**：

- 关闭后 `pipelineSceneData` 为空 → Cocos batcher2D 渲染时 `switchBufferAccessor of null` → 整个画面挂掉
- 当真机报 `readFile:fail src/effect.bin` 时，**不要**去改 patch 让它跳过 effect.bin。真正的根因是文件 mtime 太旧没被上传，删本地文件让 Cocos 重新生成就好

错误示范（已回滚）：
```js
// ❌ 不要这么改 patchRenderingSettings
delete settings.rendering.customPipeline;       // 渲染管线挂
delete settings.rendering.effectSettingsPath;
fs.unlinkSync(effectBin);                       // 只删文件本身才对
```

正确做法（保留代码不动，只手动操作）：
```bash
rm build/wechatgame/src/effect.bin
# 然后 Cocos Creator 重新构建（会重新生成 effect.bin，mtime 是最新）
# 然后 node scripts/patch-wechatgame-config.js
# 然后微信开发者工具：清缓存编译 → 预览
```

## 八、PVE 性能注意点

PVE 玩法本身是纯客户端模拟 + 关键节点云端校验，性能压力小，但有几处工程约束需要注意：

- **`pve/core/` 零框架依赖、所有随机走 `rng.ts`**——确保云端可复算（AC-13），但也意味着改 core 不能引 `cc.tween`/`cc.director` 等。
- **战报回放节奏 120ms/80ms**（详见 [UI设计与交互V1](UI设计与交互V1.md) §7.3），决定玩家"一回合体感时长"，调过快会丢信息、调过慢会拖节奏。
- **`FogMapView` 节点池**：`_rebuild` 用 `_cells`/`_rendered` 复用节点，避免每次揭示重建整张地图。
- **存档上报时机**：仅在 `FLOOR_CLEARED` 后 `saveFloorProgress`、死亡/通关时 `settleExpedition`，不在层内每步上报，避免网络抖动卡顿玩家。
- **`_checkMeta` 用 `setTimeout(0)` 调度**（2026-06-11）：原本 `_apply` 中 `await this._checkMeta(events)` 串行成就 toast × 120ms delay，单次 `_apply` 可被卡 1100+ms（真机实测）。改为 `setTimeout(() => void _checkMeta(...), 0)` 把整个调用扔到下一 macrotask；同时尝试过 `void _checkMeta(...)` 但**无效**——`void` 仍让 `_checkMeta` 的同步部分 + await microtask 抢占主线程，把 `_apply` 末尾的 `_busy=false` 推到 1157ms 后。只有 `setTimeout(0)` 才能让 `_apply` 末尾 microtask 优先处理。**真机验证**：`apply.total` 从 1159ms → 1ms。
- **toast 节奏 120→60ms / MAX 3→2**（2026-06-11）：`_playEvents` 内 `await delay(120) × 3` 是 `_apply` 唯一阻塞源。真机测 `apply.events 121ms` 每次都吃 1 次 delay，连点会感受到"按钮迟钝"。改 `TOAST_DELAY_MS=60` / `MAX_TOAST_DELAYS=2` 后最坏 `_busy` 占用 360ms → 120ms。toast 节点本身 1.6s 自动消失保留阅读时间。
- **成就 toast 合并**（2026-06-11）：`_checkMeta` 原本 `for newAch { await _playEvents([{ACHIEVEMENT_UNLOCKED}]) }`，多个成就同时解锁时后台 toast 风暴累计 N×120ms（真机测 meta 3552ms）。改为：战报栏仍逐条 push，toast 合并为一条 `🏆 成就解锁：A、B、C` 一次性展示，无 delay。
- **`_checkMeta` 调度预筛选**（2026-06-11）：连续移动 / 攻击时每次 `_apply` 都 `setTimeout(0)` 调度 `_checkMeta`，几十次排队累积主线程占用 900ms+，玩家连点偶尔 `tap.* busy=true` 被拦。加 `META_RELEVANT_EVENTS_PRESENT()` 预筛选：只在 events 含 `AP_ROLLED/KILL/OPEN_CHEST/LOOT(equip)/CLASS_ADVANCED/FLOOR_CLEARED` 时才调度（这是 `checkNewAchievements/collectCodexEntries` 真正查询的事件类型，必须与 AchievementSystem.ts 的 switch 保持同步）。MOVE/REVEAL/ATTACK/TURN_END/PLAYER_DAMAGED 等高频事件跳过，调度量减少 90%+。

### 8.1 PVE 性能埋点（排查"游戏越久越慢"用）

`ExpeditionController.ts` 顶部 `const PERF_LOG = true` 开关，输出形如：

```
[PVE perf] tap.move 0ms dir=UP busy=false
[PVE perf] apply.refreshAll 4ms events=2
[PVE perf] apply.events 124ms
[PVE perf] apply.afterApply 3ms
[PVE perf] apply.total 132ms events=2
[PVE perf] apply.meta 2ms          ← fire-and-forget，时序可能在 total 之后
```

排查口径：
- `apply.total` 持续上升 → 单次回合处理变重；细分 `apply.events`（事件回放+await delay）vs `apply.refreshAll`（map/hud diff）vs `apply.afterApply`（自动拾取/传送门）
- `tap.*` 的 `busy=true` 多 → 前一次 `_apply` 没解除，问题在上一轮（看 `apply.total`）
- `apply.events` 涨而 `events=` 数量不涨 → toast/await delay 异常，或 JS 引擎 GC 干扰
- `apply.refreshAll` 涨 → `FogMapView` 累积重绘或节点泄漏
- `apply.meta` 涨 → `updatePveMeta` 云调用排队（微信并发 5）

不需要时把 `PERF_LOG` 改 `false` 即可（保留代码，方便下次复发一行打开）。

2. 真机分包 native 加载链有 8 次重试 × 200ms intervals，最坏 ~1.6s 才回落到失败 toast，目前无 UI 进度提示。
3. `Promise.all([login, ensureResourcesBundle])` 仅覆盖登录与资源；`initWxCloud` 串行在前，理论上还能再并行一段。
4. 没有专门的"启动耗时埋点"——目前依赖 `console.log` 时间戳人工估算，建议 M2 加 `performance.now()` 节点。
