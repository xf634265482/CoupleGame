# PVE 第 7 层后输入延迟修复设计

## 背景

真机在命运远征推进到约第 7 层后，移动、攻击、交互开始出现明显延迟。用户反馈该问题在动画系统调整前已经存在，因此本次优化以“输入即时响应”优先，先处理同步热路径中的重复计算与重复渲染，表现层只做非破坏性的并行化兜底，不主动删除演出。

## 问题定位

当前输入链路中有三类会随楼层复杂度放大的同步开销：

1. `ExpeditionController._refreshAll()`
   - 每次状态变更后都会立即调用 `FogMapView.refresh()`。
   - 同时会重新计算 `_currentMoveTargets()`，其中对四个方向各执行一次 `applyMove()` dry-run。
   - 同时会重新计算攻击高亮，分别扫描怪物和实体。

2. `FogMapView.refresh()`
   - 虽然有 `_rendered` diff，但每次 refresh 仍会双层遍历整张地图。
   - `cellRenderContent()` 对每个格子都会执行 `floor.monsters.find(...)`、`floor.entities.filter(...)`。
   - 当地图从 8x8 提升到 9x9、10x10，且怪物/实体数增长时，这部分成本会在每次输入后重复放大。

3. 输入失败与轻量操作的全量刷新
   - 很多只影响一个高亮或仅用于判断的路径，仍会走到完整的 move/attack target 重算。
   - 玩家在高层频繁试探移动、攻击、交互时，这种“全量刷新 + 重复扫描”会持续堆积，体感表现为点击后半拍响应。

## 方案对比

### 方案 A：先压同步热路径，表现层仅并行化

做法：
- 把 `FogMapView.refresh()` 中按格扫描怪物/实体改为单次索引构建后复用。
- 在 `ExpeditionController` 中缓存当前可移动落点和当前攻击目标，避免每次 `_refreshAll()` 都重复做 4 次 `applyMove()` 和多次全量扫描。
- 把部分非关键 toast / 战报 / 特效等待改为并行，不阻塞输入恢复。

优点：
- 直接命中“动画前就存在”的根因。
- 不牺牲玩法，不删视觉表现。
- 风险集中在局部实现，适合先做小步验证。

缺点：
- 需要同时改 controller 和 view 两层。

推荐：是。

### 方案 B：只拆表现层串行等待

做法：
- 优先改 `_playEvents()`、toast、战报和特效播放顺序。

优点：
- 改动面小。

缺点：
- 只能缓解“拖尾”，解决不了刷新/计算本身已经过重的问题。

### 方案 C：增加性能模式开关

做法：
- 默认真机走轻量演出模式，保留后续回切能力。

优点：
- 上限高。

缺点：
- 引入额外配置和维护成本，本轮过重。

## 最终设计

本轮采用方案 A，拆成两步：

### 第一步：同步热路径瘦身

#### 1. `FogMapView.refresh()` 改为“单次索引 + 按格读取”

新增本次 refresh 内部临时索引：
- `monsterByPos`
- `entityByPos`

处理方式：
- 进入 `refresh(floor)` 时先遍历一次 `floor.monsters`，仅记录 `aiState !== 'DEAD'` 的存活怪物。
- 再遍历一次 `floor.entities`，仅记录 `!consumed` 的实体；同格仍保留现有优先级规则。
- `cellRenderContent()` 不再对每个格子执行 `find/filter`，而是改为从索引读取。

预期收益：
- 从“每格扫描怪物/实体列表”变为“每帧各扫描一次列表 + 每格 O(1) 读取”。
- 楼层越高、怪物越多，收益越明显。

#### 2. `ExpeditionController` 缓存当前输入辅助信息

新增缓存字段：
- `_cachedMoveTargets`
- `_cachedAttackTarget`
- `_cachedAttackEntityTarget`

刷新策略：
- 仅当 `_state` 变化后重建一次缓存。
- `_refreshAll()` 改为使用缓存值刷新高亮，不再每次现场重算。

实现方式：
- 提取 `_rebuildInputHints()`：
  - 统一计算四方向 dry-run 的移动落点。
  - 统一计算当前攻击怪物目标。
  - 统一计算当前冰墙目标。
- `_apply()`、`_beginNewRun()`、`_resumeRun()`、`_handleFloorCleared()` 等真正替换 state 的路径，在 `_refreshAll()` 前先调用 `_rebuildInputHints()`。

预期收益：
- 每次输入后的同步路径只做一次 hint 重建，而不是由 `_refreshAll()` 隐式重复触发。
- 避免“攻击按钮高亮”和“交互前失败提示”也不断触发同类扫描。

#### 3. 失败反馈不触发额外重算

约束：
- 移动失败、攻击失败、交互失败只允许显示提示，不触发任何新的状态刷新。
- 保持现有 `shakeToast()` 行为，但不额外调用全量 refresh。

说明：
- 当前代码大多已经满足，实施时只检查新增缓存后不要在失败分支误更新缓存或重绘地图。

### 第二步：表现层并行化兜底

只在第一步后仍有明显拖尾时启用，且不删表现：

- `_playEvents()` 中的非关键 toast、战报、浮字、轻量特效尽量并行触发。
- 只有真正影响玩法判定的阻塞弹窗继续串行。
- 输入恢复以 `_busy` 释放为准，不等待无关的收尾演出。

这一层只做“缩短阻塞”，不改变事件顺序的逻辑语义。

## 不做的事

- 不改动 PVE 数值、怪物行为、地图生成、存档协议。
- 不删除动画系统。
- 不引入新的“低画质/性能模式”开关。
- 不对云函数做任何改动。

## 风险与控制

### 风险 1：缓存与真实状态不同步

控制：
- 只在 state 真正变化后重建缓存。
- 所有使用缓存的 UI 高亮都从缓存读取，不再同时保留旧的实时扫描分支。

### 风险 2：FogMapView 索引改造后同格实体优先级变化

控制：
- 继续复用现有 `PORTAL > EXIT > KEY` 规则。
- 其他实体保持“取第一命中的现有行为”不扩大语义改动。

### 风险 3：并行化演出打乱玩家理解

控制：
- 第二步只并行非关键表现。
- 若需要削减任何已有演出，会先与用户确认。

## 验收标准

1. 第 7 层后连续移动、攻击、交互时，真机体感延迟明显下降，输入反馈更跟手。
2. 地图渲染结果、攻击高亮、移动高亮、冰墙高亮与优化前保持一致。
3. 存档、通关、死亡、跨章加载等既有流程不回退。
4. 单测保持通过，至少运行现有 Jest 全量测试。
