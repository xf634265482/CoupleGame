# 塔塔远征团 GM 数值配置中心设计

日期：2026-06-27  
范围：GM 后台第二轮扩展  
目标：在现有 GM 后台基础上，补齐玩家查询体验，并新增可视化 PVE 数值配置中心，让运营可在网页后台调整 PVE 战斗数值，不再每次改代码发版。

## 1. 本轮目标

### 1.1 解决现有 GM 页面可用性问题

- 修复当前页面中输入框无法稳定输入的问题
- 查询区改为：
  - 支持输入昵称关键词 / `userId` / `openid`
  - 支持显示最近玩家列表
  - 支持点击列表直接选中玩家
- 管理员不再需要先去云数据库翻玩家 id

### 1.2 新增 PVE 数值配置中心

- 支持在 GM 后台查看、编辑、保存 PVE 战斗数值
- 支持三层覆盖：
  - 全局默认
  - 按章节覆盖
  - 按怪物 / Boss / 玩家模板单独覆盖
- 改动只影响**后续新开局**
- 正在进行中的远征存档不追改

## 2. 明确边界

### 2.1 生效边界

本轮所有数值配置：

- 只影响“后续新开的 PVE 对局”
- 不影响已经存在的 `pve_saves`
- 不对正在进行中的存档强制追改

原因：

- 现有存档中已落入地图、单位状态、战斗上下文
- 中途换数值容易造成战斗异常或存档语义不一致

### 2.2 后台改的是“配置”，不是直接改代码

- 原有代码常量继续作为默认值存在
- GM 后台写入云数据库配置集合
- 云端在“新开局初始化”时读取数据库配置并覆盖默认值
- 没配的字段继续回退到代码默认值

### 2.3 本轮不做的内容

- 不做对进行中 `pve_saves` 的批量重算
- 不做数值版本发布流、审批流、回滚历史 diff UI
- 不做“任意字段自由写入”
- 不做全字段无边界开放编辑

说明：

- 尽管用户要求“几乎所有战斗字段都可配”，首版仍然必须走结构化白名单
- 可配字段范围可以很大，但不能放开成任意 JSON 直写

## 3. 数据方案

### 3.1 新增集合

新增集合：

- `pve_balance_configs`

建议文档结构：

1. 全局默认文档
2. 各章节覆写文档
3. 各单位模板覆写文档

文档字段统一包含：

- `id`
- `scopeType`
  - `global`
  - `chapter`
  - `unit`
- `scopeId`
  - 全局时固定 `default`
  - 章节时如 `chapter_1`
  - 单位时如怪物 / Boss / 玩家模板 id
- `enabled`
- `config`
- `updatedBy`
- `updatedByName`
- `updatedAt`
- `createdAt`

### 3.2 配置覆盖顺序

新开局读取时按以下顺序合并：

1. 代码默认值
2. 全局配置
3. 章节配置
4. 单位模板配置

后者覆盖前者。

### 3.3 配置类型

首版将 `config` 组织为结构化对象，而不是无约束平铺字段。

建议结构：

```json
{
  "playerBase": {
    "hp": 0,
    "attack": 0,
    "ap": 0,
    "armor": 0,
    "move": 0
  },
  "monsterBase": {
    "hp": 0,
    "attack": 0,
    "ap": 0,
    "armor": 0,
    "move": 0
  },
  "bossBase": {
    "hp": 0,
    "attack": 0,
    "ap": 0,
    "armor": 0,
    "move": 0
  },
  "reward": {
    "gold": 0,
    "diamond": 0,
    "destinyShards": 0
  },
  "drop": {
    "relicChance": 0,
    "equipmentChance": 0
  }
}
```

说明：

- 实际字段名必须基于代码现有可落点整理
- 不允许前端直接随意新增结构
- 云函数按白名单字段合并和校验

## 4. 现有代码接入策略

### 4.1 新开局入口接入

需要在“新远征初始化 / 战斗单位初始化”相关云端权威流程接入配置解析。

接入原则：

- 开局时一次性读取并解析配置
- 生成本局实际使用的战斗参数
- 写入本局运行态

这样后续即使后台又改配置，也不会影响已开局玩家。

### 4.2 默认值来源

默认值仍来源于当前代码中的：

- 玩家初始参数
- 怪物 / Boss 定义
- 章节战斗参数
- 奖励 / 掉落参数

数据库只做覆写层。

## 5. 云函数扩展设计

### 5.1 现有 adminTool 扩展 action

在现有 `adminTool` 中新增以下 action：

- `listPlayers`
- `listBalanceConfigs`
- `getBalanceConfig`
- `saveBalanceConfig`
- `resetBalanceConfig`

### 5.2 玩家列表查询

`listPlayers`

用途：

- 拉最近活跃玩家
- 按昵称关键词 / `userId` / `openid` 搜索

返回字段：

- `nickname`
- `userId`
- `openid`
- `lastActiveAt`
- `diamond`
- `destinyShards`
- `highestFloor`
- `hasActiveExpedition`
- 当前章节 / 层数 / 职业（如有）

### 5.3 数值配置查询

`listBalanceConfigs`

用途：

- 拉取配置列表
- 支持按 `scopeType` 分类查看

`getBalanceConfig`

用途：

- 查询某一配置详情
- 返回当前保存值
- 返回合并预览值（可选）

### 5.4 数值配置保存

`saveBalanceConfig`

输入：

- `scopeType`
- `scopeId`
- `config`
- `reason`

处理：

- 校验 token
- 校验 scope 合法性
- 校验字段白名单
- 校验数值范围
- 写入 / 更新 `pve_balance_configs`
- 记录 `admin_logs`

### 5.5 数值配置重置

`resetBalanceConfig`

用途：

- 删除指定 scope 的覆写配置，回退到上一层默认值

处理：

- 必须填写 reason
- 记录日志

## 6. 配置校验规则

### 6.1 白名单字段

所有可编辑字段必须维护在云端白名单中。

例如：

- `hp`
- `attack`
- `ap`
- `armor`
- `move`
- `critRate`
- `critDamage`
- `reward.gold`
- `reward.diamond`

是否进入首版，由代码现有结构和接入成本决定。

### 6.2 数值范围

每类字段设置上下限，例如：

- `hp`: `1 ~ 999999`
- `attack`: `0 ~ 99999`
- `ap`: `0 ~ 999`
- 概率型字段：`0 ~ 1` 或 `0 ~ 100`

### 6.3 类型限制

- 必须是数字
- 必须是整数 / 小数，按字段定义校验
- 不允许 `NaN`
- 不允许 `Infinity`
- 不允许前端传未知字段

## 7. 前端页面设计

### 7.1 查询区改造

左侧查询区改为：

1. 搜索输入框
2. 搜索按钮
3. 最近玩家按钮
4. 玩家列表
5. 点选玩家后展示玩家详情

### 7.2 数值配置区

新增一个独立面板或分页区域：

1. 配置类型切换
  - 全局
  - 章节
  - 单位
2. 配置列表
3. 配置编辑表单
4. 保存按钮
5. 重置按钮
6. 当前生效说明

### 7.3 单位配置编辑体验

单位配置建议提供：

- 单位类型筛选
  - 玩家模板
  - 普通怪
  - Boss
- 单位 id / 名称选择
- 常见字段输入框
- 高级字段折叠区

### 7.4 输入框 bug 修复原则

当前页面存在“输入框无法稳定输入”的问题，首版修复策略：

- 把搜索关键词、当前列表、当前玩家等状态显式保存在前端变量中
- 渲染后重新绑定事件时，不能把用户正在输入的值覆盖掉
- 对搜索框和表单值使用受控式状态回写

## 8. 日志与审计

所有数值配置写操作必须写 `admin_logs`：

- `action`
- `scopeType`
- `scopeId`
- `before`
- `after`
- `reason`
- `adminUsername`
- `createdAt`

建议 action：

- `saveBalanceConfig`
- `resetBalanceConfig`

## 9. 风险与对策

### 9.1 风险：字段太多导致首版失控

对策：

- 首版结构上支持完整配置中心
- 实际字段仍通过白名单逐步开放

### 9.2 风险：代码默认值与数据库配置来源冲突

对策：

- 明确“代码默认值 + 数据库覆写”的单向模型
- 不允许多来源乱覆盖

### 9.3 风险：当前局与新配置不一致

对策：

- 明确只影响新开局
- 页面提示“进行中的局不会追改”
